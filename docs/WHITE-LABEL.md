# Publish your own iOS build

This guide prepares a build for one deployment. Use [RELEASE-READINESS.md](RELEASE-READINESS.md) for the complete build/test commands, deployment inputs, privacy review and distribution evidence. The owner's batch workflow permits tested phases on `dev` before a final reviewed merge.

Mobile UX guidance is maintained in this app's `docs/mobile-auth-ux-spec.md`, and mobile motion in `tokens/mobile-motion.json`. Keep the matching inputs aligned between Android and iOS. The existing `design/` submodule supplies the original brand masters and semantic colors; mobile-specific additions do not belong in the Design repository.

1. Fork this repo and clone recursively (`git clone --recurse-submodules <repository-url>`). Keep the pinned `design/` commit unless intentionally updating the design system.
2. Edit `branding/brand.json`: set your display name, unique reverse-domain `ios_bundle_id`, Apple `ios_team_id`, HTTPS deployment origin in `server_url`, and support/privacy URLs. A null server URL asks the user on launch; a fixed URL locks the build to that deployment. Paths, credentials, queries and fragments are rejected.
3. Replace `branding/app-icon.svg` with your artwork. It must have an explicit opaque top-level background rectangle (`fill="#RRGGBB"`). The generator rasterizes to an opaque 1024 px App Store icon. Point `app_icon` to this repository-local file. Change `theme_tokens` to your light/dark semantic token JSON if rebranding the theme; preserve all semantic roles.
4. Install and select Xcode 26.2 with its iOS 26 SDKs (the CI toolchain), XcodeGen, Python 3.10+, and librsvg (`brew install xcodegen librsvg`). Run `python3 scripts/generate.py` then `xcodegen generate`. `Brand.xcconfig`, Swift constants, adaptive color assets, icons and staging schema are generated and ignored. Open the generated `SpaceWorks.xcodeproj`. Never edit or commit it.
5. Enroll your organization in the Apple Developer Program, register the bundle ID, and choose your signing team in your private build environment. Configure App Attest and Push Notifications capabilities/provisioning for that identity. Confirm development/production environments against the backend allowlist and use real hardware for attestation verification.
6. Create an APNs key in your own Apple account and configure it privately on your server. iOS uses APNs directly; it does not need a Firebase project. Self-hosters publishing Android separately need their own Firebase project for Android FCM. Push routing also needs the published native contract and server link files; see the backend dependency issue in the release guide.
7. Inject signing certificates/provisioning profiles and `.p8` files from CI secrets. Never commit keys, tokens, provisioning files, or `google-services.json`. Simulator tests use a temporary ad-hoc `LOCALCI` Keychain identity; it is not an Apple team identity or distribution credential.
8. Run the CI checks and archive a Release build using your Apple signing configuration. Check your deployment URL, dark/light themes, VoiceOver and the largest Dynamic Type size on a device. Supply support/privacy URLs and your own App Store privacy declarations, screenshots and reviewer demo account.
9. Upload an owner-signed, validated archive to your App Store Connect account and TestFlight first. Require the recorded phase checks and owner-provisioned integration tests before publication. Whole-account deletion and other missing native contracts remain release gates; an unsigned CI compile or demo journey is not a submitted build.

Optional deployment links and artwork are configured in the same `branding/brand.json`:

- `support_url` and `privacy_url` accept `null` or an absolute HTTPS URL. Leave them null until you have real deployment pages; their actions stay unavailable. The generator normalizes the HTTPS scheme and DNS host, and rejects credentials, malformed escapes, whitespace, control characters and invalid URL syntax before writing generated files. Paths, query strings and fragments are allowed for these page links; the separate `server_url` must remain an origin.
- Optional top-level artwork keys accept repository-local PNG paths in light/dark pairs. `logo_symbol` pairs with `logo_symbol_reversed`, `logo_stacked` with `logo_stacked_reversed`, and `logo_horizontal_one_colour_ink` with `logo_horizontal_reversed`. An omitted asset pair uses the original pinned Design masters. Supply both members of each configured pair. The generator checks each selected file's repository path, PNG header, dimensions (48–8192 pixels) and size (at most 20 MiB) before writing generated outputs; Xcode still needs to compile the selected images successfully.
- A custom display name uses native text in auth until you provide custom symbol or stacked artwork. Generated `hasCustomWordmark`, `hasCustomStacked` and `hasCustomSymbol` flags select the supplied auth artwork; when only one of those pairs is supplied, it is used across compact and regular layouts. Keep artwork static, undistorted and opaque, preserve its clear space, and inspect both color schemes. Android accepts SVG artwork for its equivalent symbols and stacked logos; use the corresponding platform format from the same licensed source.

Run the generator tests as well as generation after changing branding. Test a fresh build with your actual name, icon, palette, artwork, support/privacy links and bundle identifier; inspect the installed app and the Release bundle rather than only the JSON configuration. The automated fixture tests prove generator behavior with temporary inputs; they do not validate your deployment pages, signing or store submission.

App content uses the owner's supplied Gilroy native faces with Dynamic Type and Bold Text support. Native bars/system activities retain platform conventions; IDs and secrets use Gilroy with tabular digits, not a monospace family. Gilroy and the Unbounded accent font conversion provenance are in `SpaceWorks/Resources/Fonts/`; upstream licenses still apply and this repository grants no new font rights. Brand assets retain their upstream licenses; this repo does not grant additional embedding rights. Keep master logos static, undistorted and fully opaque with the Design clear space; motion belongs on sibling content and respects Reduce Motion.

Register the real Google iOS OAuth audience and optional `google_reversed_client_id` callback scheme. Enable Sign in with Apple for the registered bundle/team. Organization sign-in needs its actual native callback/device-grant contract. Compiled SDK dependencies do not enable a web-only server flow automatically. Never substitute a browser cookie or access-only response for a complete native grant.

Native capability generation supports optional `aps_environment` (`null` or `"production"`) and `associated_domains` (an explicit array of owned `applinks:`/`webcredentials:` DNS names). When push is enabled, Debug uses the development APNs environment and Release uses production. Configured capabilities require the owner's real ten-character Apple team ID and matching provisioning. Leave these inputs absent until the deployment is configured. Supply the actual associated-domain files on the owner's server; generating an entitlement does not verify them. Edit these deployment inputs instead of hand-editing generated entitlement files, which the prebuild generator recreates. See [PUSH-NOTIFICATIONS.md](PUSH-NOTIFICATIONS.md) for consent, returned registration IDs, cleanup and membership routing.

`SpaceWorks/Resources/PrivacyInfo.xcprivacy` declares same-app UserDefaults access (`CA92.1`) for locally stored preferences such as theme, server selection and introduction completion. It does not declare that production collects no data. Review app collection and linked SDK manifests against the actual deployment before store submission; [Apple's required-reason API guidance](https://developer.apple.com/documentation/bundleresources/describing-use-of-required-reason-api) explains the declaration.
